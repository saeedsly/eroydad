## ۱. آنچه واقعاً پیاده‌سازی شده و تست دارد ✅

| لایه | وضعیت | جزئیات |
|---|---|---|
| هدرهای امنیتی | ✅ | CSP (self + inline style), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`، `X-Request-ID`، بدون کش برای صفحات |
| CSRF دو لایه | ✅ | توکن فرم + بررسی Origin هم‌مبدأ → 419؛ هر دو در `security-csrf-test` |
| نشست | ✅ | کوکی `httponly + SameSite=Lax`، `secure` در HTTPS، **idle ۳۰ دقیقه + absolute ۱۲ ساعت** با `regenerate_id`؛ `session_version` برای خروج-همه؛ فهرست نشست‌های فعال در حساب |
| رمز عبور | ✅ | `password_hash` با `PASSWORD_DEFAULT` (bcrypt) + `password_verify`؛ بازیابی رمز با کلید یک‌بارمصرف و انقضا |
| 2FA | ✅ | TOTP (سکرت رمزنگاری‌شده در DB) + کدهای بازیابی؛ دخیره/بازیابی/غیرفعال‌سازی با کد‌های بازیابی در پنل حساب |
| Rate Limit | ✅ | `RateLimiter`: ورود و ثبت‌نام با سطل‌های شماره+IP (۸ شکست روی شماره) |
| XSS | ✅ | `SafeText::escape` در خروجی، `attribute()` با `ATTRS` بسته؛ تست خودکار `security-xss-test` |
| SQL Injection | ✅ | فقط PDO prepared statements در کل کد (grep بازرسی شد) |
| آپلود تصویر | ✅ | `PosterService`: سقف ۲ مگابایت، `getimagesize` + whitelist MIME، حداقل/حداکثر ابعاد، **بازنویسی واقعی تصویر** برای پاک‌سازی payload |
| کنترل دسترسی | ✅ | `requireRole(...)` روی ۵۳ مسیر admin؛ مالکیت بلیت/ثبت‌نام با HMAC و DB |
| ممیزی | ✅ | `audit_logs` با `actor/action/entity/request_id/safe_details`؛ `admin_confirmations` برای عملیات خطرناک؛ پنل `/admin/system/sessions` |
| پول | ✅ | دروازهٔ **فقط Sandbox**؛ بدون اتصال به دروازهٔ واقعی؛ `is_sandbox` ذخیره می‌شود |
| حذف داده | ✅ | سرویس Retention + پشتیبان‌گیری + استعلام؛ `docs/security/release-checklist.md` |
| امنیت در خط لوله | ✅ | دروازهٔ ۱۸ مرحله‌ای شامل `security-suite` + `acceptance-suite` |

## ۲. یافته‌های این ممیزی (بدون اصلاح)

| # | یافته | شدت | توضیح واقعی |
|---|---|---|---|
| **S1** | هدر `Permissions-Policy: camera=()` دوربین را **کاملاً مسدود می‌کند** | **بالا** | اسکنر QR (`BarcodeDetector` + `getUserMedia` در `checkin.js`) روی این هدر در مرورگر واقعی `NotAllowedError` می‌گیرد؛ یعنی «اسکن با دوربین» عملاً در استقرارِ با هدرهای فعلی **از کار افتاده** (ورود دستی جایگزین کار می‌کند). اصلاح هدف: `camera=(self)` در فاز پیاده‌سازی با تأیید. |
| **S2** | اِعمال مجوزها نقش‌محور است نه مجوزمحور | **بالا** | `requireRole` سطح نقش؛ کدهای مجوز (۲۲ عدد) ذخیره می‌شوند اما `assert` مجوز در مسیرها نیست. ریسک: تغییر نقش = دسترسی کاملِ آن نقش بدون ریزکنترل. هدف: default-deny با `requirePermission` روی هر مسیر. |
| **S3** | CSP با `style-src 'unsafe-inline'` | متوسط | لازم برای CSS درون‌خطی قالب‌ها؛ در فاز هدف: nonce/فایل‌های CSS جدا |
| **S4** | بدون گزارش خودکار آسیب‌پذیری/بدون HSTS | متوسط | HSTS فقط در HTTPS لازم است و باید در فاز استقرار اضافه شود |
| **S5** | کلیدهای حساس در `.env` (DB، `APP_KEY`، `TICKET_SIGNING_KEY`) | کم | الگوی درست؛ `.env` خارج از گیت؛ `.env.example` بدون رمز ✓؛ ریسک = استقرارهای دستی |
| **S6** | رمز دوم (`two_factor`) با سکرت رمزنگاری‌شده؛ بازیابی با کدهای هش‌شده | کم | الگوی درست؛ اطمینان از رمزنگاری سکرت در فاز پرداخت واقعی هم حفظ شود |
| **S7** | یادآوری‌ها «تنبل» (روی دیدن صفحه) | کم | ریسک امنیتی نیست؛ مشکل قابلیت اطمینان است (ثبت در TECHNICAL_DEBT) |
| **S8** | بدون لاگ ساختاریافتهٔ فایل/بدون SIEM | متوسط | `audit_logs` در DB هست؛ خروجی فایل/الگوریتم مانیتورینگ نیست |

## ۳. آنچه از نظر امنیتی **وجود ندارد** (برای فاز ۰۹)

1. کلید API و احراز API عمومی
2. امضای وب‌هوک ورودی/خروجی
3. محافظت Brute-force فراتر از شماره (مثلاً captcha/proof-of-work در شرایط حمله)
4. رمزنگاری داده در حالت سکون (PII مانند national_id) — فعلاً در DB ساده
5. اسکن وابستگی‌ها/به‌روزرسانی خودکار (بدون Composer هم ندارد — نقطه قوت ضمنی)
6. تست نفوذ مرورگری (فقط تست تابعی خودکار)

## ۴. اولویت‌بندی امنیتی برای فاز پیاده‌سازی

- **P0:** S1 (دوربین)، S2 (مجوزمحوری)، امضای وب‌هوک پرداخت
- **P1:** S3 (CSP تمیز)، S4 (HSTS)، S8 (لاگ ساختاریافته)، رمزنگاری PII
- **P2:** گزارش خودکار آسیب‌پذیری، SIEM، تست نفوذ
